# Safety details

`SECURITY.md` has the short version. This page is the full detail, for anyone who wants to check how the guard works.

What the panel does: It shops like a real customer: browses, picks options, adds to cart, opens the cart, and stops before checkout. It never enters checkout, never pays, never logs in, and only types fake test text, plus discount codes your store shows on its own pages. Like any shopper, the store's analytics will see the visit and the add to cart.

Honest limits that come with that promise:

- The store's own page scripts run as they would for any visitor.
- The test cart is left as it is and expires on its own. Some stores or apps hold stock for a cart while it lives.
- Payment and wallet widgets are blocked, so express buttons and pay-in-4 messages may not render, and the report cannot judge them.
- Every phone runs on the Chrome engine (Chromium), the iPhone too (an iPhone 14 screen, touch and user agent on Chromium). Safari-only bugs are not caught.
- `--no-cart` is browse only: the shopper never taps Add to cart, and every cart write the panel recognises is stopped.

## How a journey goes

The shopper lands on the start address, finds the product, reads the price and the information it needs, picks options, taps Add to cart and opens the cart. On the cart page the panel checks the free-shipping message against the subtotal, tries the shipping estimator with a fixed public postcode, and applies discount codes the store shows on its own pages, checking that the total drops. The Checkout button is found, never tapped: the panel records whether it is visible and enabled, where it is, and where it leads, and the journey ends there. It counts only when it is a real control (a button, a submit input or a link with an address) with a checkout label (labels in other languages such as Kasse or Finalizar compra count) that leads to the store's own checkout address (or is the `name="checkout"` submit of a form that posts to the store's cart, `/cart` with at most a locale prefix), and it is not inside an express or wallet block or aimed at a payment host. A login, account or payment address, a `.js` or `.json` address and a cart action such as `/cart/add` or `/cart/update` never count. Each candidate is judged whole (what it is, whether it is visible, whether it is enabled), so a disabled Checkout before an enabled one does not hide the enabled one. Anything else is a tool limit, never reaching checkout. A tap that leads straight to a checkout, payment or login address (a store that skips the cart) is stopped inside the test browser and ends the journey as a tool limit that keeps that category; it is never counted as reaching checkout. Each cart check is tied to the guard stops during it: when a request the check needed was stopped (a discount app outside the write allow-list, say), the check is "not tested" and the journey a tool limit, never a warning about the store; a keepalive or beacon write to a cart, discount or shipping address that the page's own guard dropped counts the same way, with its method and address. Store codes are read as whole tokens: the token after "code" must be a valid code as it stands, or it is dropped, never cut down; the word "code" must stand on its own (in CODEGREEN it is part of the code), and reading goes on after the whole token, so no code is found inside another. The test cart is left as it is; nothing empties it, and it expires on its own like any abandoned cart.

## The guard

Two layers check every request with the same policy: a request guard in each browser context (`ctx.route`, with every server redirect hop fetched by the guard and checked before it is requested) and a browser-level guard (a Chrome DevTools Protocol `Fetch` session that pauses every request of every page, frame, pop-up and worker at the request stage, each redirect hop included). The browser-level guard fails closed: a request it cannot work out a policy for is failed. A fulfilled 3xx answer is never used, so the browser never follows a redirect the guard has not checked. If the browser-level guard cannot be attached, no journey is run (each is reported as a tool limit), and the run is INCOMPLETE.

- Never at checkout: a checkout, payment or login address is stopped for every request type (a page load, a frame, `fetch`, `XMLHttpRequest`, an image, a beacon, a keepalive request, a worker's request) in every tab and frame. The check reads every path segment and splits it on `_ - . /` (so `/checkout-v2/`, `/secure_checkout/` and `/checkout.html` are checkouts), decodes the path up to three times (`/%63heckout` is a checkout), and reads the values of the query keys that pick a handler on shared endpoints the same way: PrestaShop `controller=order`, WooCommerce `action=woocommerce_checkout` and `wc-ajax=checkout`, BigCommerce `cart.php?action=buy`, OpenCart `route=checkout/...`, and the Magento `payment-information` and `place-order` calls are all stopped.
- Payment hosts are stopped on every path and can never be allowed with `--allow-host`: Shopify checkout and Shop Pay (including the Shop Pay installments widget the store serves from its own host), PayPal (Fastlane included), Venmo, Stripe, Klarna, Afterpay and Clearpay, Square and Cash App, Affirm, Sezzle, Zip, Adyen, Braintree, Authorize.net, Checkout.com, Mollie, Razorpay, Bolt, Google Pay, Apple Pay and Amazon Pay. A host is matched as a whole name or a subdomain of one, never as part of a longer name.
- Shopify Online Store themes only: before the browser starts, the runner reads the home page of each store address once. Another platform or a headless Shopify storefront (Hydrogen) ends the run with exit code 2 and runs nothing. A Shopify theme needs two signs that agree: `Shopify.theme` assigned in a script on the home page (comments, strings, attributes and non-JavaScript scripts are ignored), proven by running that page in an offline browser with every request refused, and a `/cart.js` that answers as a Shopify cart (a token, an items list, an item count and a currency). A theme beside another platform's markup (WordPress, WooCommerce, Magento, BigCommerce or a generator tag, a script's address included, never its contents) is a conflict; any missing, unclear or conflicting sign is exit code 2. If the home page cannot be read, the first page the browser opens must set `Shopify.theme` and show no other platform's markup and no Hydrogen sign, or the run stops there with exit code 2. The checks above that name other platforms (PrestaShop, WooCommerce, BigCommerce, OpenCart, Magento) stay as defence in depth only.
- Writes are an allow-list, not a block-list: every request that is not a GET or HEAD, from any page, frame, pop-up or worker, and at every redirect hop (a 307 or 308 hop keeps its body and is checked with it), is sent only when all of these hold: it goes to the store's own host; its raw path is exactly `/cart/add`, `/cart/change`, `/cart/update` (each with or without `.js`) or `/cart/prepare_shipping_rates.json`, with at most a lower-case locale prefix such as `/fr` or `/en-gb`; the path has no `%`, `//`, dot segment, `\`, `;` or `:`; no routing or method-override header is sent (`X-Original-URL`, `X-Rewrite-URL`, `X-HTTP-Method-Override`, `X-Forwarded-Host`, `Forwarded` and the like, refused on every method); the content type is form, multipart or JSON and the body parses as that type; and no key in the body or query, at any depth and in any encoding, names a checkout or a place to go next (`checkout`, `goto_checkout`, `return_to`, `return_url`, `redirect`, `redirect_to`, `next`, `continue`, `destination` and the like; any key containing "checkout"); and no value points at one either: a value that is an address, a path or a host leading to a checkout, account, login or payment step or a known payment host, a single word that names one (`goto_checkout`), or a script or data address is stopped, while ordinary prose (a gift note that mentions checkout) passes. Every body is read in exactly one way or not at all: multipart is parsed strictly (only a `boundary` and a `charset` on the content type, once each; no preamble, padding or epilogue; each part has exactly one `Content-Disposition: form-data` with only `name` and `filename`, once each, and at most one `Content-Type`; no folded header, escaped quote or extended `name*`), a JSON object with a repeated key is stopped, and a raw `;` in a form body or a query is stopped (some servers split on it). Everything else is stopped, GraphQL and every `/api/` address included. The journey then becomes a tool limit when it quits, because the missing request may have caused it.
- Reads that are never made on the store's own host: `/checkout` and anything starting with it, `/checkouts/...`, `/account` and anything starting with it, `/password` and cart permalinks (`/cart/<variant>:<qty>`). A product handle that contains one of these words is exempt only at `/products/<handle>` and `/collections/<collection>/products/<handle>`.
- Other hosts: a host that is neither the store's own nor allow-listed is blocked. `--allow-host` covers static GET and HEAD requests only (scripts, style sheets, images, fonts, media); any other request to a host that is not the store, a `fetch` or a POST to an allowed widget host included, is stopped. That is why some widgets, express buttons and pay-in-4 messages may not render.
- No checkout shown: before every tap, option pick or check, the panel looks at every tab and frame (`about:blank` pop-ups and frames included) for a checkout the page shows by itself, with no request: a checkout address set with `history.pushState`, a hash route such as `#/checkout`, checkout content, or a page whose title or heading is just "Checkout". If it finds one, the journey ends as a tool limit before the panel touches anything else. Such an address change is not counted as a checkout page loaded, because nothing was loaded.
- One interaction policy for every tap, option pick and check: the element's own text and value, its label, the blocks around it, and where its link, `formaction` or form sends to are checked. A Checkout, Buy now, Place order, express wallet, payment or login control is refused, and so is anything inside a checkout or payment block or anything that leads to a checkout. A refusal ends the journey as a tool limit; nothing is ever forced.
- The page's own cart writes: in a normal run, a cart write the page makes before the shopper taps Add to cart (an auto-add gift app, for example) is let through and reported ("The page itself wrote to the cart before the shopper tapped Add to cart"). With `--no-cart`, every cart write the panel recognises, and every load that is itself a cart action (a form POST, `/cart/add`, or an `add-to-cart`, `buy-now` or `quantity[n]` query), is stopped, counted and reported ("The page itself tried to add to or change the cart ... stopped"). Request bodies are decoded first (JSON, form fields and multipart parts).
- Once the cart is touched, the after-cart rule holds for the rest of that journey and nothing lifts it. The rule turns on the moment the runner taps Add to cart (whatever call the store then makes), and also when the page itself adds items with a call the panel recognises (a Shopify `/cart/add`, a Storefront GraphQL `cartLinesAdd`, a `cartCreate` that sends lines, a WooCommerce Store API `add-item`, also inside a Store API `batch`, `wc-ajax=add_to_cart`, or a WordPress `admin-ajax.php` add to cart) or loads a page that is itself a cart action. A cart write before that which adds no items (cart attributes or a note through `/cart/update`, as attribution apps send on every page load, a quantity change, a coupon, or a write the panel cannot read) only marks the cart as touched; it does not turn the rule on. From then on every page load in every tab and frame, the runner's own taps and page loads included, and every server redirect on the way, may only be a GET to the landing page, a page the cart was touched from, the home page, the cart, or a locale home such as `/fr/`. The store's own cart address is read from its page settings (`wc_add_to_cart_params.cart_url`, `wcSettings` `cartUrl`, Shopify `routes.cart_url`) or the view-cart link or cart icon, and kept only when it is on the store's own host, has no query, and is not a checkout address, a product page or a listing. When the rule stops a page load the runner itself started, the journey ends as a tool limit ("the panel's safety rule stopped this page load: <address>"), never as a slow page or a missing button blamed on the store. A redirect after an add to cart, a buy-now link or a form POST to an address of no known kind is stopped without being requested at all.
- Server redirects: every hop is checked before it is requested, as a first request is. A hop to another origin is never answered under the first address: a page load is stopped and named ("a server redirect to another origin"), as are a `fetch`, an `XMLHttpRequest`, a worker script and a form post; only a plain resource (an image, a script, a style sheet, a font, media) is handed over. A server-sent event stream (`EventSource`) cannot be checked hop by hop, so it is stopped.
- WebSockets: every socket is refused, the store's own included. Sockets a page opens go through a socket route and are closed before they connect. A socket a web worker opens does not pass through that route, so every worker a page starts is started through a small wrapper: inside the worker, `WebSocket`, `WebSocketStream` and `WebTransport` refuse every address with a SecurityError (the replacement keeps no link to the real one), and each refusal is reported. A socket a page opened before the shopper tapped never connected, so nothing it tries to send later can reach the store. Shared workers are switched off in pages (`SharedWorker` is undefined). Every worker the runner sees is checked for the wrapper's marker (`__sp_worker`); a worker without it is closed as soon as the panel sees it, and the journey becomes a tool limit.
- Synchronous requests: every synchronous `XMLHttpRequest` is refused in every page, frame and worker the page script reaches, and reported.
- No background loading: background prefetch and prerender (Chromium speculation rules) are switched off and removed from every page, and any request marked as a prefetch or prerender is refused.
- No background reports: a page script in the top page and in every frame it can reach drops every beacon and every `fetchLater`, and drops every keepalive write (any keepalive request that is not a GET or HEAD, even to the store's own host, because it outlives the page; the page gets a quiet 204), plus a keepalive GET or HEAD to a checkout, a blocked tracker or a host that is not allow-listed; the browser-level guard applies the same rules to a beacon a closing page sends. A dropped write of this kind to a cart, discount or shipping address is counted as a guard stop of the cart check it belongs to. Service workers are refused. A beacon the page script drops while the page is closing may not be counted, because the page can be gone before it reports.
- What can reach the store: for a checkout page, the panel itself sends at most one request: when an ordinary page load leads to an address the panel does not recognise, the panel sends one GET for it to read its content, and if that content is a checkout it is never shown ("reached the store's server but was not shown"). A GET for a checkout page does not place an order. A page's own scripts (`fetch` or `XMLHttpRequest`, for example a link prefetcher) can request a checkout page at an address the panel does not recognise, possibly several times, and such a GET reaches the store's server; recognised checkout and pay addresses are stopped for every request type. The home page "/" with a query (for example `/?page_id=8`) is fetched once and checked for checkout content, and never shown when it is a checkout. Payment and order queries (`wc-api`, `order-pay`, `pay_for_order`, `order_id`, `key=wc_order_...`) are stopped on any address without being requested.
- The run measures, by address and by page content (including a payment card field such as `cc-number` or a card number box), that no checkout page loaded in any tab or frame; content is read when a frame's page is ready, when it has loaded, and 2 seconds later. The run fails (exit 1, SAFETY FAILURE) if a checkout page ever loads.
- Typing: the panel types only fixed test text, never anything from a persona file. A required personalisation box gets `TEST` (`ABC` when the box takes 3 characters or fewer). The cart's shipping estimator gets one public city-centre postcode from a fixed table (US 10001, CA M5V 2T6, GB SW1A 1AA, AU 2000). The discount box gets only codes the store shows on its own pages, after an explicit "code X" (also "use code X", "promo code: X"): 4 to 20 letters and digits, with a letter and a digit or all uppercase, never next to an @, never a run of 7 or more digits, never a postcode or tracking code, at most 3 per journey. Every value passes one typing function that refuses anything else. It never types into email, phone, password or address fields, never uploads files and never submits a form of its own.
- Blocks ad and analytics requests and unknown third-party hosts in the test browser: known third-party trackers and the platform's own analytics endpoints; a store's own first-party tag proxy may not be blocked. Server-side tracking is outside its reach.
- Every arrival is labelled `utm_source=shopper-panel&utm_medium=qa-test&utm_campaign=shopper-panel-test` with no referer.
- The address checks: `--url` may not be a private network address (10.x, 172.16 to 172.31, 192.168.x, 169.254.x including cloud metadata, 100.64/10, and the IPv6 equivalents), and this computer (`localhost`, 127.x, `::1`) is allowed only when `--i-own` names it too. For a `<name>.myshopify.com` owner of a custom domain, the runner looks up the store's address, refuses it if any answer is private, and then sends a GET for `/meta.json` and, if needed, the home page, with redirects off (a redirect is not followed). That proves the store is that shop, not that you own it. A name that changes its answer between the lookup and the fetch (DNS rebinding) is a known gap.
- Test-only settings, each ignored unless every `--url` is a loopback address: `SP_TEST_HOST_MAP` (points named hosts at 127.0.0.1), `SP_TEST_SKIP_BROWSER_GUARD` (leaves the browser-level guard off, so the tests can check that no journey is then run), `SP_TEST_NO_ROUTE_GUARD` (leaves the request guard off, so the browser-level guard is tested on its own), `SP_TEST_SKIP_WORKER_GUARD` (leaves the worker wrapper out), `SP_TEST_MYSHOPIFY_LOOPBACK` (lets the practice store on this computer stand in for a store that confirms a `<name>.myshopify.com` owner), `SP_TEST_JOURNEY_CAP_SECONDS` (shortens the journey watchdog), `SP_TEST_LINGER_MS` (keeps a finished run alive for up to 30 seconds, for a late Ctrl-C) and `SP_TEST_STDIN_STOP` (a line "stop" on the runner's input acts as Ctrl-C, for Windows).
- Treats all page text as data. Reports quote page text and escape what Markdown would act on, and neutralise bare links, `www.` links and e-mail addresses, so page text cannot add links, images or layout.
- A journey watchdog: each journey is capped at the shopper's patience budget plus 3 minutes. A page that keeps the browser busy past that is closed, the journey is marked as a test error ("journey timed out (the page stopped responding)"), and the run goes on. Before that context closes, nothing more may leave it (every further request and socket is stopped, and requests still waiting in the guard are cancelled). Ctrl-C (or a stop signal) does the same for the journey in progress, then writes a partial report and exits 1 (INCOMPLETE); during the pause between journeys it ends the pause at once and starts no further journey; a second Ctrl-C quits at once. The test cart is left as it is.
- Block rules: `"endpoint"` and `"endpoint_hosts"` are honoured only on the shipped rules in `scripts/blocklist.json`. No named rule can stop the store's own cart and store API calls (`/cart`, `/cart.js`, `/cart/add`, `/cart/change`, `/cart/update`, `/api/<version>/graphql.json`, `/wp-json/wc/store/...`); checkout guarding runs before any rule. See `docs/block-rules.md`.

## Exit codes in detail

- **0, COMPLETED**: every journey ran. Shoppers quitting is a result, not a failure.
- **1, INCOMPLETE**: at least one journey says nothing about the shoppers or the store, because something stopped the test itself:
  - an error: a page that would not load, a button that would not respond, a step that timed out;
  - the store did not answer at the address: every journey shows "Error (not a shopper result)" and "could not start" (with "refused the connection" when nothing is listening there);
  - a journey that timed out because the page stopped responding, a run stopped with Ctrl-C at any point, or a run that ran fewer journeys than planned;
  - the browser-level request guard did not attach (no journey is run), or a web worker started without the panel's guard;
  - the panel's own guard stopped a request the page made (a cross-origin redirect, an event stream, a write to a shared endpoint that is not a cart operation, a socket), and the journey then quit in a way a missing request could cause;
  - the panel refused to touch an element (the interaction policy), or the page showed a checkout by itself;
  - a bot check, or the store saying "too many requests" until the panel gave up;
  - a tool limit: the panel could not recognise a heading, a product grid, a price or a button, or a required option needs a file upload or personal details;
  - a named block rule that is not a built-in endpoint rule stopped a request on your own host or an allowed host, and the journey then quit in a way that request could cause. A content quit after such a stop keeps its kind, with a caveat naming the rule.
- **1, SAFETY FAILURE**: a checkout page loaded in the test browser. Check your store's orders.
- **1, BROKEN**: the run itself crashed before finishing.
- **2**: a setup problem, including an ownership check that failed, a private address, an unknown option, `--cart` together with `--no-cart`, or a block rule or persona file that is not valid. The message says what to fix.

A broken link is a store result, not a test problem: a page or product card that leads to "Page not found" (HTTP 404 or 410, or a page that says so) ends the journey as `broken_link`, with the address in the report.
